## 1. 評価概要

土木・建設会社（従業員約600名・IT/DX部門7名・公共80%/民間20%）で本番運用可能な水準かを、
18指標・競合代替率・リスクの観点から総合評価した。評価は「ソース/画面/DB/API/設定/依存/テスト/
CI/CD/Git履歴/ドキュメント」を精査し、**実装済みの証拠**と**未実装・未確認**を分離して行った。
README 上の計画（承認フロー・版管理・RBAC 等）と実装状況の差異を重点確認している。

### 重要な検出事項（改善前）

1. **重大（権限逸脱）**: `PATCH /api/v1/projects/{project_id}/containers/{container_id}` が
   プロジェクト所属チェックを欠いており、**別組織の利用者が他社コンテナのタイトル・分類を書き換え可能**。
   実証テスト（クロス組織 PATCH → 200 OK）で確認した（改善後に 404 化）。
2. **重大（誤表示）**: ダッシュボード・プロジェクト詳細・承認タスク・アップロード・監査ログの
   主要画面がモックデータ（`designData.ts`）を表示し、ダッシュボードの KPI・コンテナ数・適合率・
   メンバー・活動履歴・監査ハッシュチェーン等は**実データではない**。経営層向け表示として誤判断の恐れ。
3. **高**: 承認 UI・アップロード UI が実 API と未接続（操作しても DB に反映されない）。
4. **高**: 自己登録が本番ガード対象外（誰でもアカウント作成可）、OIDC JIT プロビジョニングに
   ドメイン制限がない。
5. **高**: RBAC（ロール/権限）は管理 API・UI のみで、**エンドポイントの権限強制には未接続**。
6. **中**: 版管理（ContainerRevision）が未使用、ファイル一覧・削除 API なし、識別子の重複登録を許容。

## 2. プロジェクト概要

| 項目 | 内容 |
|---|---|
| 名称 | Open BIM 情報基盤（Open BIM Information Platform） |
| 目的 | ISO 19650 に基づく BIM 情報の一元管理（CDE: 作業中→共有→承認済み→保管） |
| 主な利用者 | 現場施工管理者・設計/土木技術者・本社管理部門・経営役員・監査担当・協力会社（予定） |
| 業務課題 | 版違い図面の使用・ファイル上書き・承認記録の散逸・監査証跡不足・命名規則不統一 |
| 提供価値 | 承認済み情報のみ現場へ到達、版・状態・監査ログの一元管理、命名規則の自動検証 |
| 技術スタック | FastAPI/Python 3.11・React 19/TS/Vite 7・PostgreSQL 15・Redis・MinIO・ClamAV・Docker Compose |
| 完成段階（README 記載） | 機能 PoC〜限定パイロット準備段階（本番運用の正本としては未到達） |
| 運用段階 | 本番環境・ドメイン・Secrets 未確定（Issue #31 がブロッカー） |

### 完成段階の実態評価

- **実装済み（証拠あり）**: JWT 認証+リフレッシュローテーション、OIDC PoC（PKCE）、RBAC 管理 API/UI、
  監査ログ（Append-Only トリガー）、CDE 状態遷移（行ロック）、命名規則検証、ファイルアップロード
  （SHA-256・MIME 許可・ClamAV）、バックアップ/復元演習、production 起動ガード、8 ジョブ CI。
- **未実装/未接続**: 承認・アップロード画面の実 API 接続、ダッシュボードの実データ表示、版管理
  （リビジョン）機能、検索、通知、ファイル一覧/削除 UI、ユーザー管理（本評価で API 化）、
  権限強制、パスワード変更、監査ログ外部 WORM/署名。

### 総合判定（改善前）

**PoC（機能 PoC〜限定パイロット準備段階）**

理由: 中核バックエンドの堅牢性（監査・排他制御・認証）は本番素養がある一方、
**権限バイパス（IDOR）1件の実証**、主要画面のモック表示、承認/アップロードの未接続により、
現状のまま本番利用すると誤判断・権限逸脱・監査欠落のリスクがある。
README の「本番運用の正本としては未到達」という自己評価は妥当と確認した。

## 4. 強み（15 件）

1. 監査ログの Append-Only 設計（PostgreSQL トリガーによる UPDATE/DELETE 拒否）が実装・CI 検証済み。
2. 承認ワークフローの並行処理安全性（`SELECT ... FOR UPDATE` による親→承認→コンテナのロック順序）。
3. production 起動ガード（弱い秘密鍵・DB/MinIO 資格情報・localhost CORS を拒否）。
4. JWT アクセス/リフレッシュ分割+ローテーション+失効（revoked_tokens）。
5. OIDC 認可コード+PKCE の PoC 実装（Entra ID / HENNGE 連携の土台）。
6. アップロードの多層防御（MIME/拡張子許可・Stored XSS 防止・SHA-256・ClamAV・500MB 上限）。
7. ISO 19650 Annex A に基づく命名規則エンジン（必須/任意セグメントの先読み解決・プロジェクト別ルール）。
8. クロス組織アクセスに 404 で存在を隠蔽する設計思想（大半のエンドポイントで実装済み）。
9. 暗号化バックアップ（AES-256-CBC）と隔離環境復元演習の実績（RTO 15 秒・SHA-256 一致検証）。
10. 8 ジョブ CI（lint/型/テスト/依存監査/SBOM/E2E/gitleaks）が全 green、STABLE 実績。
11. 文書体系が充実（README・要件定義・詳細仕様・IT_SETUP・運用手順・ADR 4 件・SLI/SLO・Runbook）。
12. 構造化ログ（structlog）・ヘルスチェック（DB/Redis）・monitor.sh による運用スクリプト。
13. 認証失敗・登録・状態遷移等の主要操作が監査ログに記録される（失敗系も記録）。
14. Docker Compose の本番/ステージング/復元演習/デモを分離し、migrate ワンショットを組み込み。
15. 依存監査・ライセンス/SBOM・gitleaks を CI に常設し、秘密値の Git 混入を防止。

### AI 設計方針（追加を目的化しない）

- **AI 不要領域**: 命名規則チェック（ルールエンジン）、状態遷移の妥当性、権限制御、
  監査ログ記録はルール・検索・決定論的処理で対応し AI を使わない。
- **時間削減優先**: ① 検索（RAG: 承認済み文書・仕様書への質問応答、引用必須）、
  ② 命名規則の自動提案（ルール+過去実績）、③ 監査ログの異常パターン検知（ルールベースから開始）。
- **モデル構成**: 外部 LLM API 利用時は Azure OpenAI/Entra ID 連携を前提に、データ送信禁止領域を
  事前定義。社内文書は VPC/プライベートエンドポイント経由、機密区分は RAG 対象外。
- **安全性**: 根拠引用（チャンク ID・文書 URL）・信頼度表示・人間承認（承認ワークフローに統合）・
  権限制御（RAG の閲覧権限と同一フィルタ）・プロンプトインジェクション対策（システムプロンプト固定、
  文書内容を命令として扱わない、入出力サニタイズ）・PII/機密のマスキング・入出力監査（監査ログ連携）・
  誤判定時の責任分界（AI は支援のみ・最終判断は人間）・利用量/予算上限・停止スイッチ。
