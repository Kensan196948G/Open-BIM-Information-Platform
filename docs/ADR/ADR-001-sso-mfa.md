# ADR-001: 認証統合（Entra ID / HENNGE）とMFAの考え方

- ステータス: **Draft（社内ID基盤・HENNGE管理者との確認後に Accepted へ）**
- 決定日: 2026-08-05
- 対象: 認証・アイデンティティ基盤

## 背景

現状はローカルJWT＋bcryptのみで、600名規模＋協力会社の運用にはアカウント停止漏れ・
パスワード攻撃・退職者残存のリスクがある。評価レポートでもSSO/MFAはP0に位置づけられた。

## 判断

1. **OIDC（Authorization Code + PKCE）を標準の認証経路とする**。
   - 自前のパスワード認証・MFA実装は行わず、IdP側の条件付きアクセス/MFAに委ねる。
   - HENNGE One が組織のゲートウェイである場合、HENNGE → Entra ID のフェデレーション経路を
     既存管理者と確認し、本アプリは Entra ID の OIDC エンドポイントのみに接続する（二重統合を避ける）。
   - HENNGE が直接 OIDC を提供する構成が確認できた場合は、同一のOIDCクライアント実装で接続先を
     切り替える（設定変更のみ）。
2. **JIT（Just-In-Time）プロビジョニングは最小限にし、原則は事前割当**。
   - 初回ログイン時に `email` で既存ユーザーと紐付け、未登録ユーザーは `is_active=false` で作成する。
   - 協力会社は sponsor 制の招待フロー（Phase 1）まで受け付けない。
3. **SCIM によるアカウントライフサイクル同期は Phase 1 の採用候補**。
   - 退職者即時遮断は、Entra ID 側のアクセスレビュー＋条件付きアクセスで担保し、
     SCIM はスケジュール同期で補完する（リアルタイム性はIdPのセッション失効に依存）。
4. **MFAはIdPの条件付きアクセスポリシーで強制**。本アプリはTOTP等を実装しない。

## 結果

- パスワード・鍵・MFAポリシーの管理責任がIdP側に集約され、退職・停止・再発行の運用が軽減される。
- IdP選定・テナント・フェデレーション構成の決定が必要（本ADRは設計上の前提を固定するもの）。
- ローカルパスワード認証は、IdP障害時のフォールバックとして管理者判断で無効化できるよう設定で制御する。

## PoC（本ブランチで実装済み）

`backend/app/services/oidc.py` に汎用OIDCクライアント（discovery / PKCE / token / userinfo）を実装。
`/api/v1/auth/oidc/authorize`・`/api/v1/auth/oidc/callback` を追加し、`OIDC_*` 環境変数があれば有効化される。
IdPクレデンシャルが用意され次第、実テナントでエンドツーエンド確認する。
